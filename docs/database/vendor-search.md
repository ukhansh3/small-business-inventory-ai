# DB-SEARCH-001 — 업체 지도 탐색 데이터/권한 명세

- 상태: **기존 migration 기반 현재 구현 설명 + 향후 검증 항목**
- DB 정본: `supabase/migrations/202610280001_vendor_registration.sql`
- API: `GET /api/v1/vendors`, `GET /api/v1/vendors/{id}`
- DB RPC: `public.search_published_vendors`, `public.get_published_vendor`

## 읽기에 관여하는 주요 테이블
| 테이블 | 역할 | 화면 사용 |
|---|---|---|
| `public.vendors` | 업체 ID, `current_revision_id`, `hidden` | 현재 공개 업체 판정 |
| `public.vendor_revisions` | 업체 정보·승인 상태·좌표·설명 | 업체명, 주소, 지도 좌표 등 |
| `public.item_revisions` | 해당 revision 품목·가격·규격·배송비·확인일 | 카드 품목·가격/상세 |
| `public.vendor_images` | revision 이미지 참조 ID와 순서 | 업체 카드/상세 이미지 |
| `public.vendor_members` | 실제 소유 관계 | 조회보다는 본인 관리 권한 판정 |
| `app_private.staff_roles` | 실제 운영자 권한 | 승인/검토 영역(지도 공개 조회의 별도 기능) |

이 문서는 실제 테이블을 **설명**하는 명세이며 SQL 구조의 정본이 아니다. 수정은 새 migration으로 처리한다.

## 조회 불변조건
1. `vendors.hidden = false`.
2. `vendors.current_revision_id`가 현재 승인된 `vendor_revisions`를 가리킴.
3. `vendor_revisions.status = 'approved'`.
4. 공간 검색에는 유효한 지리 좌표(`location`)가 존재하고 지정 반경에 포함.
5. `item_revisions.selling=true`인 품목만 공개 응답 포함.
6. 시연용 `mvp_demo`/`synthetic` 데이터와 실제 `live` 업체를 같은 승인 자료처럼 혼합하지 않음.
7. 조회 결과는 거리 오름차순 + 업체 ID 안정 정렬, 기본 20건 단위.
8. 과거 승인본, 미승인 수정본, 내부 검토 메모, 비공개 사진 원본 경로를 일반 조회에서 반환하지 않음.

## 현재 인증 및 시연 설계의 경계
- 현재 RPC `search_published_vendors`와 `get_published_vendor`는 `auth.uid()`가 없으면 거부한다.
- 앱 요구는 **로그인 UI 없이 시연 시작**이므로, 서버와 RLS가 보호 가능한 인증된 자동 세션 또는 별도 시연 백엔드가 필요하다.
- 별도 게스트 세션에 실제 운영자 권한/`service_role`을 부여하지 않는다. 운영자 시연 작업은 격리된 데이터/정책에만 허용.
- 게스트 시연 초기화는 시연 데이터만 대상으로 하고 `live` 테이블의 승인 업체를 삭제/수정하지 않는다.

## 검색 관련 DB 변경 필요성
지도 중심 화면, 카드, 스와이프 시트와 **승인된 핀 라벨 정책(검색 전 업체명만, 단일 일치 품목 검색 후 해당 품목 가격)** 및 **지도 조작 후 버튼 탭으로 재검색하는 트리거** 자체는 **DB 스키마 변경이 필요하지 않다.** 단, 가격 대표 품목 선정·배송 필터·지도 viewport 검색·새로운 데이터 소스 조합을 확정하면 현재 RPC와 contract를 함께 변경할 수 있다.

## 테스트 필수
- 숨김/미승인 업체 검색 제외.
- 좌표 없음 핀 제외, 지도 목록 ID 일치.
- 범위 경계 100/20000 미터, offset 0/20 등.
- 가격/배송비 null 오인 금지.
- 최신/오래된 가격 확인일 처리.
- 개인 위치·검토 내부 메모·비공개 사진 경로 유출 금지.
- 익명 시연 세션과 일반/운영 계정 교차 접근 차단(데모 설계 완료 후).

## 다중 일치 품목 UI 승인사항 (2026-11-04)
- 한 업체에서 검색어와 일치하는 품목이 여러 개인 경우 핀은 일치 품목 개수만 표시하고, 하단 카드에서 각 품목별 가격을 보여준다.
- 이 변경은 현행 공개 `items[]`를 화면에서 필터링해 구현할 수 있으므로 **DB migration 변경 필요 없음**.
- 특정 품목을 임의로 선택하거나 `MIN(price)`로 대표 가격을 생성하지 않는다.

## 지도 범위 조회 정책 (Q-SEARCH-07 A 확정)
- `이 지역 검색` 버튼의 검색 범위는 현재 화면에서 보이는 카카오 지도 사각형(bounds)이다. 3km 고정 반경 검색으로 대체하지 않는다.
- **현재 RPC는 중심·반경(100~20000m) 기반이므로 정확한 bounds 조회를 아직 지원하지 않는다.**
- 경계 좌표 검증·가시 영역 내 공간 조건·기존 승인/숨김/좌표 필터 유지·안정 정렬·결과 수 제한을 포함하는 새로운 DB 쿼리 설계를 검토한다.
- 새 migration과 Zod/Route 계약을 함께 승인·수정해야 한다. 기존 적용 migration은 변경하지 않는다.
- 지나치게 넓은 가시 영역, 좌표가 날짜변경선을 넘는 사례, 결과가 20개를 초과하는 경우는 추후 확정·테스트한다.

## 지도 클러스터링 관련 DB 영향 (Q-SEARCH-10 A)
- 클러스터링 자체는 위치를 가진 공개 업체들의 **화면상 묶음**이며, 이 승인만으로 DB 테이블·컬럼 추가가 필요하다고 보지 않는다.
- **Q11 A안 확정:** 지도에는 현재 적용한 bounds의 전체 공개 업체를 누락 없이 전달하고, 목록만 20건 단위로 제공해야 한다. 현재 검색 RPC의 20건 제한은 목록용 동작으로는 적합하지만 지도 전체 클러스터 원천으로 사용하기에 불충분하다. 추가 RPC/경량 마커 projection/서버 집계 방식은 미결정이며 별도 설계 및 승인 대상이다.
- 클러스터에 포함되는 ID는 해당 결과에서 유효한 공개 업체여야 하며, 숨김·미승인·좌표 없는 업체는 포함하지 않는다.

## Q11 전체 지도 / 20건 목록의 DB 원칙
- 같은 `bounds + query + category + 출처` 조건에서 **동일한 공개 조건**(승인된 현재 revision, `hidden=false`, 유효 좌표, RLS/권한)을 지도·목록에 적용한다.
- 지도에 제공하는 데이터는 마지막으로 적용된 bounds의 **전체 일치 업체**를 대표해야 한다. 페이징된 목록 20건을 전체 결과로 오인하지 않는다.
- 목록은 **20건 단위**로 안정적이고 중복 없는 순서로 조회한다. **Q12 A 확정:** 마지막으로 적용된 가시 지도 영역의 중심점으로부터 거리 오름차순, 거리 동률은 기존 RPC와 같이 업체 ID를 보조 정렬 키로 사용한다. 전체 결과를 이 기준으로 정렬한 뒤 페이지를 자른다.
- 구현 방법을 결정하면 기존 적용된 migration을 덮어쓰지 않고 새 migration으로 인덱스/RPC를 추가한다. 실제 DB 권한 정책을 우회해서 전체 조회하는 방식을 허용하지 않는다.
- 미결정: 광역 bounds 최대 검색 범위, 업체 수 상한, 마커 projection와 집계/분할 조회 방식, 데이터 변경 중 페이지 간 일관성 기준.

## Q12 A — 목록 거리순 정렬 DB 원칙
- bounds 필터로 선택된 공개 업체에 대해 마지막 적용된 지도 가시 영역의 **중심점 기준 거리**를 계산하고, 거리 오름차순으로 반환한다. 중심점은 디바이스 현재 위치가 아니다.
- 동거리 업체는 **업체 ID 오름차순**으로 보조 정렬해 결정적인 페이지 경계를 만든다(현행 `search_published_vendors`의 정렬 원칙 유지).
- `LIMIT 20`은 전체 정렬 및 필터를 적용한 이후에 수행한다. 첫 페이지만 거리를 계산하거나 각각의 페이지에 새 중심을 적용하지 않는다.
- 공간 검색 RPC 계약의 상세 함수명/파라미터, 페이지 스냅샷·커서 구현, 결과 상한은 아직 승인되지 않았다. 기존 적용된 migration 파일은 수정하지 않는다.

## Q13 A — 클러스터 탭과 DB 변경 범위
- 클러스터 탭은 **기존 조회된 업체 집합의 카메라 확대/클러스터 재계산을 위한 UI 동작**이다. 그 자체로 새 테이블, 컬럼, RPC 또는 DB 요청을 추가하지 않는다.
- `이 지역 검색`을 눌러 새 가시 영역을 적용하는 경우에만 기존에 확정한 bounds 조회 확장 설계를 통해 데이터를 갱신한다. Q9/Q11에서 미해결인 전체 업체 조회·범위 상한은 그대로 남아 있다.

## Q14 A — 접힌 결과 요약바와 DB 영향
- 첫 실행 시 접힌 결과 요약바 노출 및 핀 탭 → 선택 카드 변경은 **프론트엔드 상태 변화**다. 이 결정만으로 새 DB 테이블·컬럼·RPC는 요구되지 않는다.
- 요약바의 전체 업체 수는 Q11에서 확정한 동일한 공개 조건과 가시 영역의 **전체 고유 업체 수**로 계산해야 한다. 현재 20건 페이지 수를 전체 개수로 간주하지 않는다. 정확한 집계 방식은 기존 Q11 미해결 데이터 조회 계약에서 정한다.

## Q15~Q24 DB 영향 평가 (2026-11-04)
- **DB 변경이 직접 필요 없는 UX:** Q15 목록 선택/카메라, Q16 시트 목표 높이, Q17 키보드 제출 타이밍, Q20 기본 위치, Q21 빈 결과 화면.
- **검색 SQL/RPC 수정 또는 검증 필요:** Q18 업체 유형·품목·배송 필터의 정확한 공개 데이터 매칭, Q19 품목 검색 시 가격순(비교 규격/기준 결정 후), Q24 대량 가시 영역 조회 및 정확한 전체 업체 집계. 기존 승인/숨김/RLS 조건을 그대로 적용한다.
- **스키마 확인 필요:** Q22 가격 미확인 값 표현은 현재 품목 `price` 숫자 계약과 충돌 가능. 0으로 채우지 않으며 허용 정책 승인 전 DB 변경하지 않는다.
- **별도 기능으로 설계:** Q23 업체 저장은 게스트 세션별 격리 저장이 필요하다. 공개 실데이터·다른 게스트의 저장 상태를 변경하지 않도록 독립 테이블/정책을 향후 `saved-vendors` 명세에서 정한다.
- **운영 안전:** 기존 migration 수정/삭제 금지. 필요시 새 순차 migration만 추가하며 실제 운영 데이터/권한을 손대지 않는다.
