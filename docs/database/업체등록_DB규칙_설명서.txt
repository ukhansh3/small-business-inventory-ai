천하장사 — 업체 등록과 DB 규칙 설명서
작성일: 2026-10-28

1. 이번에 결정한 서비스 방식

공급업체 사장이 자기 업체와 판매 품목·가격을 직접 등록합니다.
운영자가 내용을 확인하고 승인하면 음식점 사장들이 볼 수 있습니다.
업체마다 판매 품목과 가격이 반드시 있어야 합니다.

위 세 가지는 사용자가 결정한 제품 방향입니다.
아래 세부 저장 구조와 수정·승인 방식은 구현을 위한 제안입니다.
이 문서는 설명서이며, 실제 Supabase 테이블이나 권한을 생성하지 않습니다.
실제 사용자 수요가 검증되었다는 의미도 아닙니다.

2. 전체 흐름을 쉽게 보면

업체 사장 가입
→ 내 업체 작성
→ 품목과 가격 등록
→ 검토 요청
→ 운영자 확인
→ 승인된 업체·품목·가격 공개
→ 음식점 사장이 지도와 상세 화면에서 확인

작성 중에는 정보를 덜 입력해도 저장할 수 있게 합니다.
단, 검토를 요청할 때는 필수 정보가 모두 있어야 합니다.
검토 중이라는 이유만으로 지도에 먼저 공개하면 안 됩니다.

3. DB에 나누어 저장할 것

[로그인 계정: Supabase Auth]
이메일, 로그인 정보, 비밀번호 관리 등을 맡습니다.
앱이 별도 테이블에 비밀번호를 복사해 저장하지 않습니다.

[사용자 프로필: profiles]
- 사용자 ID: 로그인 계정과 연결하는 고유 번호
- 표시 이름
- 생성일, 수정일
운영자 권한은 가입 화면에서 본인이 선택할 수 없습니다.
운영자 지정은 신뢰할 수 있는 서버 절차로만 처리합니다.

[업체 관리 권한: vendor_members]
- 업체 ID
- 사용자 ID
- 역할: 소유자 또는 관리 담당자
어떤 사람이 어떤 업체를 수정할 수 있는지 판단하는 표입니다.
사장 여부를 화면에서 선택한 값만 믿지 않고 이 연결을 확인합니다.
다른 업체의 관리자로 자신을 마음대로 추가할 수 없게 합니다.
초기에는 업체 생성자만 소유자로 연결하는 방식을 권장합니다.
추가 관리자 초대·소유권 이전은 별도 기능으로 결정합니다.

[업체 기본 식별 정보: vendors]
- 업체 ID
- 생성일
- 현재 공개 중인 승인본 ID
업체의 고유 번호는 정보가 수정되어도 유지됩니다.
업체명만으로 같은 업체인지 판단하지 않습니다.
사업자등록번호 수집·증빙 보관·사업자 확인 방식은 아직 미결정입니다.

[업체 정보 제출본: vendor_revisions]
- 제출본 ID, 업체 ID, 작성자 ID
- 업체명, 소개, 분류
- 공개용 연락처, 업체 주소, 위도·경도
- 영업시간과 배송·방문 수령 조건
- 상태, 제출일, 검토자, 검토일, 보완 사유
한 업체의 처음 등록과 나중 수정 내용을 버전별로 저장합니다.
공개 연락처와 업체 주소는 사장이 공개하기로 한 정보만 받습니다.
계정의 개인 연락처를 업체 정보에 자동으로 복사하지 않습니다.
좌표가 없으면 임의 위치에 지도 핀을 만들지 않습니다.
좌표는 서버에서 주소를 변환해 확인하고 저장하는 방식을 권장합니다.

[판매 품목 식별 정보: vendor_items]
- 판매 품목 ID, 업체 ID
업체가 파는 상품을 식별하는 번호입니다.
예를 들어 A업체의 양파와 B업체의 양파는 서로 다른 판매 품목입니다.
공통 품목 분류표와 연결할 수 있지만 업체별 상품을 하나로 합치지 않습니다.

[제출본별 품목·가격: item_revisions]
- 품목 버전 ID, 제출본 ID, 판매 품목 ID
- 품목명, 분류
- 판매 규격: 예를 들어 10kg, 1박스
- 규격 수량과 단위: 예를 들어 10 / kg
- 해당 규격 1개 가격과 통화: 초기에는 원화 정수 금액 권장
- 부가세 포함 여부
- 최소 주문 개수
- 배송비와 배송비 적용 기준
- 판매 여부, 가격 확인일
- 정보 제공자와 제공 시점
가격은 업체 사장이 제공한 정보라는 출처를 남깁니다.
양파 10kg 한 상품의 가격인지, 1kg당 가격인지 구분해서 저장합니다.
동일 업체의 상품인지와 해당 제출본의 업체가 같은지도 DB에서 검사합니다.

[업체 사진: vendor_images]
- 제출본 ID, Storage 파일 경로, 표시 순서, 대표 사진 여부
사진 파일은 Supabase Storage에 저장하고 DB에는 경로를 저장합니다.
검토 전 사진도 비공개이며 승인된 제출본의 사진만 공개합니다.
사진 파일 주소를 안다는 이유만으로 미승인 자료를 읽을 수 없게 합니다.
삭제된 제출본의 사진 정리는 연결 여부를 확인한 뒤 처리합니다.

[검토 기록: review_events]
- 대상 제출본 ID
- 검토한 운영자 ID
- 승인 또는 보완 요청
- 사유와 처리 시각
누가 언제 어떤 내용을 승인했는지 남깁니다.
기록을 지우거나 이전 승인 기록을 다른 내용으로 덮어쓰지 않습니다.
업체 숨김·재공개 같은 운영 조치도 별도 기록으로 남깁니다.
운영자 내부 메모와 사장에게 전달할 보완 사유를 분리합니다.

4. 등록 상태는 이렇게 구분합니다

작성 중(draft)
사장이 작성하는 단계입니다. 사장과 운영자만 볼 수 있습니다.

검토 대기(pending_review)
검토 요청이 완료된 단계입니다. 일반 이용자에게 공개하지 않습니다.
제출한 내용은 고정하고, 수정하려면 제출을 취소해 작성 중으로 돌립니다.

보완 필요(changes_requested)
운영자가 수정할 내용을 전달한 단계입니다.
사장이 고친 뒤 다시 검토 요청합니다.

승인(approved)
운영자가 확인한 제출본입니다.
이 승인본이 업체의 현재 공개본으로 지정되어야 실제 노출됩니다.

숨김(hidden)
운영자가 업체 공개를 중단한 상태입니다.
승인 이력이 있어도 숨김 상태면 지도·검색·상세에서 노출하지 않습니다.
숨김 해제는 운영자만 처리하고 이유와 시간을 남깁니다.

일반 공개 조건:
“운영자가 승인함 + 현재 공개본으로 지정됨 + 업체가 숨김 상태가 아님”
세 조건을 모두 만족해야 합니다.
상태 이름과 실제 스키마 배치는 구현 시 공용 계약에서 확정합니다.

5. 검토 요청 전에 꼭 갖춰야 할 정보

업체명, 분류, 공개용 연락처, 업체 주소, 정상적인 지도 좌표를 받습니다.
판매 중인 품목이 최소 1개 있어야 합니다.
판매 중인 모든 품목에는 품목명, 규격·단위, 가격,
부가세 조건, 최소 주문 개수, 가격 확인일이 있어야 합니다.
배송·수령 조건도 명시해야 합니다.

예: “양파 / 10kg 1포 / 18,000원 / 부가세 포함 / 최소 1포”
위 금액은 구조를 설명하기 위한 가상 예시입니다.

가격을 비워 둔 채 ‘가격 문의’로 공개하는 방식은 이번 요구에 맞지 않습니다.
가격 미입력은 0원이나 무료로 바꿔 저장하지 않습니다.
일반 판매 가격은 0보다 큰 금액을 받는 것을 권장합니다.
무료 상품을 허용하려면 별도 정책을 먼저 정합니다.

배송비는 품목 가격과 분리합니다.
배송비 0원은 무료 배송, 미입력은 미확정입니다.
조건부 배송비는 조건을 함께 보여주고 최종 합계로 단정하지 않습니다.
서로 다른 규격·단위·세금 조건의 상품은 가격만 보고 자동 비교하지 않습니다.

6. 승인 후 수정은 어떻게 하나요?

권장 방식은 “공개 중인 승인본”과 “새로 작성하는 수정본”을 분리하는 것입니다.

예:
현재 공개: 양파 10kg 18,000원
사장이 변경 제출: 양파 10kg 19,000원
검토 중: 공개 화면에는 기존 승인 가격 18,000원 유지
운영자 승인: 업체 정보와 품목·가격을 새 승인본으로 함께 교체

사장이 승인된 행의 가격을 직접 수정하게 만들면 운영자 확인을 우회합니다.
그래서 수정은 새 제출본으로 저장하고, 승인된 내용은 고정합니다.
이전 가격은 과거 이력으로 남기고 현재 가격처럼 노출하지 않습니다.
이 승인 대기 방식은 제안이며 팀이 구현 전에 확인해야 합니다.

가격 변경 심사가 늦어지면 기존 가격이 실제와 달라질 수 있습니다.
공개 화면에 가격 확인일과 주문 전 재확인 안내를 표시합니다.
더 이상 유효하지 않은 정보를 즉시 비공개하는 철회 기능도 권장합니다.
철회는 공개를 줄이는 행동이며, 새로운 정보의 재공개는 승인 후에 합니다.
철회 범위와 검토 처리 목표 시간은 별도로 정합니다.

7. 접근 권한 규칙

일반 이용자:
승인된 현재 공개본과 그 품목·가격·사진만 조회합니다.
미승인 제출본, 내부 검토 메모, 개인 계정 정보는 조회하지 못합니다.
비로그인 상태에서도 공개 조회를 허용할지는 별도 결정입니다.

업체 사장:
자신이 관리하는 업체의 초안 작성·수정·검토 요청만 가능합니다.
남의 업체 수정, 스스로 승인, 운영자 권한 부여는 불가능합니다.
검토자·검토일·현재 공개본을 직접 바꾸지 못합니다.

운영자:
제출 내용을 확인하고 승인·보완 요청·숨김을 처리합니다.
본인이 관리하는 업체의 셀프 승인은 막고 다른 운영자가 확인하도록 권장합니다.

화면에서 버튼을 숨기는 것만으로 권한을 구현하지 않습니다.
서버에서도 검사하고 DB의 RLS(행별 접근 규칙)와 Storage 권한으로 제한합니다.
업체에 접근 가능한 사람이 품목·사진에도 접근하도록 연결해서 검사합니다.
서버 관리자 키는 RLS를 우회할 수 있으므로 서버의 권한 검사가 특히 필요합니다.
브라우저나 Android 앱에 관리자 키를 포함하면 안 됩니다.

8. DB가 반드시 막아야 하는 잘못된 상태

- 없는 업체나 다른 업체의 제출본에 품목을 연결하는 것
- 빈 품목명, 음수 가격, 잘못된 수량·단위
- 판매 중 품목이 하나도 없거나 필수 가격이 빠진 업체를 승인하는 것
- 사장이 승인 상태나 공개본 ID를 직접 설정하는 것
- 승인되지 않은 제출본을 공개본으로 지정하는 것
- 검토가 끝난 제출본을 사장이 나중에 몰래 고치는 것
- 동시에 승인 요청이 들어와 일부 품목만 다른 버전으로 공개되는 것

승인할 때는 관련 정보 확인과 공개본 교체, 검토 기록 저장을
하나의 DB 작업 묶음(트랜잭션)으로 처리합니다.
실패하면 전체를 취소하고, 성공하면 전체가 함께 적용되어야 합니다.
승인할 제출본을 고정하고 중복 처리를 막아 재요청에도 안전하게 만듭니다.
업체 생성과 생성자 권한 연결도 한 번에 처리합니다.

9. 빠르고 안정적으로 조회하려면

지도 위치에는 PostGIS 공간 인덱스를 둡니다.
공개 상태·업체 분류·업체 ID·제출본 ID·판매 품목 연결에도
조회에 필요한 인덱스를 둡니다.
지도 범위와 필터에 맞는 공개 업체만 서버에서 검색합니다.
전체 업체를 휴대폰에 내려받아 골라내는 방식은 피합니다.
지도와 목록은 같은 검색 결과를 사용합니다.
가격 이력 전체와 비공개 검토 내용을 목록 응답에 넣지 않습니다.
한 번에 표시할 개수를 제한하고 다음 페이지를 이어서 받습니다.
숨김·승인·가격 변경 뒤에는 관련 캐시를 갱신해 이전 정보 노출을 줄입니다.

10. 구현 후 확인할 테스트

1) 사장 A가 사장 B의 업체와 품목을 수정할 수 없는가?
2) 사장이 스스로 운영자가 되거나 자기 제출본을 승인할 수 없는가?
3) 검토 중인 업체·가격·사진을 주소를 직접 호출해도 볼 수 없는가?
4) 품목 또는 가격이 빠진 업체의 검토 요청과 승인이 거부되는가?
5) 승인하면 업체 정보와 품목·가격이 같은 버전으로 공개되는가?
6) 수정본 검토 중에는 기존 승인본이 유지되는가?
7) 숨김 처리 후 검색·지도·상세·사진에서도 공개가 중단되는가?
8) 승인 실패 시 공개본과 검토 기록이 일부만 바뀌지 않는가?
9) 동시에 두 번 승인해도 공개 버전이 꼬이지 않는가?
10) 좌표가 없거나 잘못된 업체가 지도에 임의로 표시되지 않는가?
