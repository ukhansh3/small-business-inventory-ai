# API-SEARCH-001 — GET /api/v1/vendors

- 상태: **현재 main 코드 기준 확인된 계약**; 데모 비로그인 요구는 별도 미구현 변경사항
- 코드: `apps/cheonhajangsa/app/api/v1/vendors/route.ts`
- DTO: `packages/vendor-contracts/index.ts`의 `searchQuerySchema`, `publishedSearchSchema`
- DB RPC: `public.search_published_vendors`

## 목적
승인된 현재 공개본이며 숨김 상태가 아닌 업체를 기준 좌표와 반경, 검색어, 카테고리로 검색한다. `mvp_demo` 또는 `synthetic` 자료는 이 응답에 섞지 않는다.

## 요청
`GET /api/v1/vendors?latitude=37.2834&longitude=127.0465&radius=3000&query=%EC%96%91%ED%8C%8C&category=&offset=0`

**현재 인증**: `Authorization: Bearer <Supabase access token>` 필수. 사용자 요청의 로그인 화면 없는 시연 모드와는 별개의 미구현 과제다.

| Query | 타입 | 필수 | 기본값 | 검증 |
|---|---|---|---|---|
| latitude | number | 필수 | 없음 | 유한수, -90~90 |
| longitude | number | 필수 | 없음 | 유한수, -180~180 |
| radius | integer | 선택 | 3000 | 100~20000, 미터 단위 |
| query | string | 선택 | `""` | trim, 100자 이하 |
| category | string | 선택 | `""` | trim, 60자 이하 |
| offset | integer | 선택 | 0 | 0~100000 |

정의되지 않은 query 키는 현재 Zod `.strict()`에 의해 거부된다. UI의 `배송 가능` 필터는 현재 API에 없는 필드이므로 임의로 전송하지 말 것.

## 200 응답 — 타입 계약
```ts
{
  vendors: Array<{
    id: UUID; revision_id: UUID;
    name: string; description: string; category: string;
    contact: string; address: string;
    latitude: number; longitude: number;
    opening_hours: string;
    fulfillment: 'pickup'|'delivery'|'both';
    delivery_terms: string;
    items: Array<{
      id: UUID; name: string; specification: string;
      quantity: number; unit: string; price: number;
      currency: 'KRW'; tax: ''|'included'|'excluded'|'exempt';
      minimum_packages: number;
      delivery_fee: number|null;
      delivery_fee_basis: string;
      checked_on: 'YYYY-MM-DD'; source_type: 'vendor_provided';
    }>;
    image_ids: UUID[];
    distance_m?: number;
    data_kind: 'live';
  }>;
  offset: number;
  limit: number;       // 현재 DB RPC는 20
  data_kind: 'live';
}
```
위는 이해를 돕기 위한 타입 표기이며 구현의 전체 진실 원천은 공유 Zod 스키마다. 새 필드 추가는 API 문서만 수정하지 말고 Zod·서버·모바일·테스트를 함께 변경한다.

## 현행 검색·정렬 규칙
- `vendors.current_revision_id`가 가리키는 승인 상태 `vendor_revisions` 중 `hidden=false`이며 유효 좌표가 있는 업체만.
- 중심 좌표부터 `radius` 미터 안에 있는 업체.
- `category`는 업체 카테고리 일치, `query`는 업체명 또는 판매 품목명에 대한 부분 문자열 검색(대소문자 구분 없음).
- 거리 오름차순, 같은 거리면 업체 ID로 정렬. `LIMIT 20 OFFSET offset`.
- 결과가 없으면 200 + `vendors: []`, 장애인 경우 오류를 반환.

## 주요 오류
- 401 `UNAUTHENTICATED`: Bearer 누락·만료·무효.
- 422 `INVALID_INPUT`: 누락된 필수 좌표, 범위 초과, 잘못된 query.
- 503 `DATABASE_NOT_READY`, `DATABASE_UNAVAILABLE`, `DATABASE_CONTRACT_MISMATCH`, `AUTH_UNAVAILABLE`, `SERVER_NOT_CONFIGURED` 가능.
- 500 `INTERNAL_ERROR`: 예상하지 못한 서버 예외.

오류 기본 구조:
```json
{"error":{"code":"INVALID_INPUT","message":"입력값을 확인해 주세요.","fieldErrors":[{"path":"latitude","message":"..."}],"requestId":"..."}}
```
`fieldErrors`는 검증 오류에만 있을 수 있다. `Cache-Control: private, no-store` 적용.

## 명세 변경 예정/미결정
- **시연 버전 로그인 없이 진입:** API가 아직 Bearer 인증을 요구하므로 인증된 자동 세션/격리 경계 검토 필요. 단순히 RLS 우회나 `service_role` 공개로 해결하지 말 것.
- **사용자 승인:** 지도 드래그·확대·축소 후 `이 지역 검색` 버튼을 보여주고 클릭 시에만 이 검색 API 호출. 지도 조작 이벤트만으로 API를 재호출하지 않는다.
- **승인 Q-SEARCH-10(A):** 지도 표시에 클러스터링을 적용하고 줌인 시 개별 핀으로 분리한다.
- **승인 Q-SEARCH-11(A):** 전체 일치 업체가 지도·클러스터의 원천이고 목록만 20건 단위로 점진적 조회. 현행 API의 `limit=20` 응답 하나를 전체 마커로 사용하면 요구사항 위반이다. 구체적 조회 API/집계/상한 정책은 별도 승인 후 확정한다.
- **승인 Q-SEARCH-12(A):** 하단 목록 기본 정렬은 마지막 적용된 지도 가시 영역 **중심점으로부터의 거리 오름차순**. 20건씩 페이지를 넘겨도 중심 좌표와 정렬 기준을 유지해야 한다. 현재 API의 거리순+업체 ID 보조 정렬은 이 동작에 부합하지만 기존 반경 검색만으로는 bounds 검색에 부족하다.
- **승인 Q-SEARCH-07(A):** `이 지역 검색` 탭 시 현재 지도 화면에서 보이는 사각형 영역(bounds)을 기준으로 검색한다. 현재 API는 `latitude`·`longitude`·`radius`만 지원하므로 새 지역 검색 계약/DB RPC 변경 검토가 필요하다.
- 배송 필터 역시 사용자 승인 전 추가 금지.
- **사용자 승인된 핀 정책:** 검색 전 `업체명`만, 품목 검색 결과에 일치 품목이 하나인 경우 그 품목·가격 표시. 이 표시는 기존 응답의 `vendors[].items[]`를 이용한 UI 변환이므로 API 필드를 바로 추가할 필요는 없음. 다만 각 업체의 items 배열은 검색 결과 품목만 담는 것으로 보장되지 않아 UI가 `items[0]`을 임의 선택해서는 안 됨.
- 동일 업체 다중 품목 일치 시에는 핀에 일치 개수만, 카드에서 각 품목 가격을 보여주는 정책이 승인됐다. 가격 비교나 최저가 선정 API를 새로 만들지 말 것.
- RN↔WebView 내부 지도 마커 메시지 계약 변경은 `docs/ui/screens/vendor-search.md`를 참조할 것.

## UI 결합 규칙 — 검색 품목 다중 일치 (2026-11-04 사용자 승인)
- **API 계약 변경 없음.** 현행 `vendors[].items[]`는 해당 업체 공개 품목 전체를 포함할 수 있다.
- 앱은 `query`와 `items[].name`을 대소문자 무시 부분 문자열로 비교해 **일치 품목 수를 계산**한다. 업체명 일치만으로 품목 수를 부풀리지 않는다.
- 검색어 없음: 업체명만 표시. 일치 품목 1개: 그 품목과 가격. 일치 품목 2개 이상: 핀에는 `일치 품목 N개`만 표시하고, 선택한 하단 카드에서 일치한 품목별 가격을 모두 표시한다.
- 이 표현 정책을 구현하기 위해 DB에 `matching_item_count`나 대표 가격 컬럼을 임의 추가하지 않는다. 서버 측 매칭 배열 추가는 추후 실제 성능 요구가 확인될 때 별도 승인한다.

## 지도 이동/재검색 UI 호출 규칙 (Q-SEARCH-02 승인)
- 지도 이동·줌 자체는 현재 업체 검색 HTTP 요청을 발생시키지 않는다.
- `이 지역 검색` 탭에서만 새 지역을 조회한다. 선택한 검색어·분류를 유지하며 `offset=0`으로 요청을 시작한다.
- 한 번의 사용자 탭에 중복 호출이 나가지 않도록 방지하고 응답이 역전돼도 가장 최근 요청 결과만 적용한다.
- **Q-SEARCH-02는 요청 발생 시점에 관한 결정이다. Q-SEARCH-07에 따라 정확한 viewport 검색용 요청 계약을 별도로 설계·승인해야 한다.**

## 가시 영역 검색을 위한 API 변경 계획 (Q-SEARCH-07 A, 구현 미완료)
- 확정된 **사용자 관점 동작**: `이 지역 검색` 클릭 시 현재 화면에 보이는 지도 bounds 기준으로 검색한다.
- 현행 서버 Query(`latitude/longitude/radius`)는 원형 범위를 지원하며 사각형 bounds 조건을 표현하지 못한다. 카카오 WebView의 가시 영역을 서버에서 처리할 수 있는 형태로 전달해야 한다.
- **권장 계약 방향(제안, 아직 구현·승인 전):** 경계값 `south`,`west`,`north`,`east`를 가진 bounds 기반 요청 모드를 추가하고, 기존 중심·반경 요청 모드는 호환성을 위해 유지하는 방안을 검토한다. 정확한 파라미터 이름·혼용 금지 규칙·최대 범위·경도 -180/180 처리·정렬/페이지 규칙은 후속 명세 결정으로 확정한다.
- 기존 `vendors[]` 응답의 업체/품목 필드는 우선 재사용 가능하다. 다만 `limit=20`이므로 **화면 전체 업체를 마커로 표현하기 위한 결과 처리**는 별도 설계가 필요하다.
- UI와 DB 필터 결과가 같아야 하고, 화면 밖 결과를 '이 지역 검색 결과'로 표시하지 않는다.
- Zod `searchQuerySchema`, Route Handler, Supabase RPC, 프론트 엔드 호출, 계약 테스트를 함께 바꿔야 한다. 기존 적용된 migration을 수정하지 않고 새 migration을 추가한다.

## 클러스터 표시 및 데이터 완전성 (Q-SEARCH-10 A)
- 지도 클러스터는 특정 응답 `vendors[]`의 **서로 다른 업체 ID**로 구성하며, 클러스터 숫자는 업체 수를 뜻한다.
- 품목 개수(`일치 품목 N개`)와 업체 클러스터 숫자는 별개이다.
- **Q11 A 승인:** 지도·클러스터용 데이터는 현재 적용된 bounds에 일치하는 전체 업체의 유일 ID를 포함해야 한다. 하단 목록 전용 페이지는 20건씩 제공한다. 현행 `LIMIT 20 OFFSET` 응답 하나는 목록의 1페이지에만 대응하며 전체 지도 데이터가 아니다.
- 구현 전 승인 없이 새 `clusterCount` 필드나 집계 API, 최대 결과 상한, 응답 스키마를 임의로 확정하지 않는다.

## Q-SEARCH-11 A — 지도 전체 업체 / 목록 페이지 계약 (설계 요구, **미구현**)
### 사용자 승인 결과
- 지도 마커·클러스터 집합: **마지막으로 사용자가 검색을 적용한 가시 bounds 안의 전체 일치 공개 업체**.
- 하단 업체 목록: 같은 조건으로 **20개씩 다음 페이지**를 로딩한다. 목록을 페이지 이동/추가로 읽어도 지도 마커는 같은 전체 집합을 유지한다.
- 지도·목록은 같은 필터·출처·공개 정책·결과 기준을 사용하며, 클러스터 숫자는 **중복 제거한 실제 업체 ID 개수**다.

### 현행 구현과의 차이
- 현재 `GET /api/v1/vendors`의 DTO와 DB RPC는 **중심·반경 + `LIMIT 20 OFFSET`**만 지원한다. Q11 A와 Q9 A를 만족하려면 API 계약·Zod·Route·DB RPC·모바일을 함께 변경해야 한다.
- **미확정 구현 선택지:** (1) 경량 마커용 전체 결과 API/모드 + 20건 목록 API, (2) 서버에서 전체 ID를 안정된 페이지로 수집 후 완전성 확인, (3) 클러스터 서버 집계와 목록 페이지를 분리. 어느 것도 승인된 엔드포인트나 DTO로 간주하지 않는다.
- **후속 명세 필요:** 정확한 bounds 파라미터, 검색 스냅샷/페이지 일관성, **확정된 거리순을 안정적으로 이어갈 커서/offset 설계**, 최대 결과 수·최대 범위·시간 제한, 과대 결과 오류 및 로딩 UI.
- 서버는 조회된 일부 20건만으로 전체 클러스터 수를 가장해서는 안 된다. 완료되지 않은 조회는 부분 결과임을 표시하거나 계약된 완전성 확보 후 전체를 표시해야 한다.

## Q-SEARCH-12 A — 하단 목록 정렬 계약 요구 (사용자 승인, 신 API 미구현)
- **기준점:** 사용자가 마지막으로 `이 지역 검색`을 눌러 성공 적용한 지도 가시 영역의 **중심 좌표**. 단말 GPS 좌표, 지도 조작 중 새 중심, 임의 기본 지점으로 대체하지 않는다.
- **순서:** 이 기준점으로부터 각 검색 일치 업체까지의 거리 **오름차순**. 같은 거리일 때 기존 RPC가 사용하는 **업체 ID 오름차순** 동률 처리를 연속 적용해 페이지 순서가 결정적이어야 한다.
- **페이지:** 전체 조건에 일치하는 검색 목록을 위 순서대로 정렬한 뒤 `20`건 단위로 제공해야 한다. 두 번째 페이지부터 중심/검색어/필터/적용 bounds가 달라져서는 안 된다.
- **범위:** 기존 반경 API는 중심 기반 거리순을 이미 지원한다. Q9에서 확정된 bounds 검색용 신규 요청 계약을 정의할 때도 거리 기준 중심을 함께 유도/전달하는 규격이 필요하다. 정확한 필드명은 아직 승인되지 않았다.
- **보류:** 페이지 경계 사이 DB 데이터가 변할 때의 스냅샷/커서 전략, 기타 선택 정렬 옵션, 최대 조회 건수.

## Q13 A — 클러스터 탭은 지도 클라이언트 이벤트 (HTTP 변경 없음)
- 사용자 승인: 숫자 클러스터를 탭하면 클러스터 영역으로 지도 이동·확대, 이후 `이 지역 검색` 버튼 표시.
- **클러스터 탭/줌 자체는 업체 검색 API 요청 트리거가 아니다.** 검색은 사용자 버튼 탭으로 최신 가시 bounds를 적용할 때 발생한다.
- 별도 `GET /clusters` 또는 서버 측 클러스터 확대 엔드포인트는 Q13만으로 확정하거나 추가하지 않는다. 현재 지도의 전체 업체 집합 확보 계약(Q11)은 별도의 미해결 API 과제로 유지한다.

## Q14 A — 첫 진입 접힌 결과 요약바(화면 결합)
- 시트의 초기 상태와 핀 선택 시 카드 전환은 **모바일 UI 상태 관리 변경**이며, 이 결정 자체로 신규 API 엔드포인트나 DB 필드가 승인되는 것은 아니다.
- 접힌 요약바가 `주변 업체 N곳`을 표시할 때 `N`은 **Q11의 동일 검색 조건에 일치하는 전체 고유 업체 수**를 의미한다. 현행 목록 API 첫 페이지 20건을 전체 건수로 해석하면 안 된다.
- 전체 업체 수를 클라이언트 전체 마커 집합으로 구할지, 서버의 정확한 count 필드로 받을지는 **Q11 데이터 조회 계약 설계에서 미결정**이다. 결과 완전성이 미확인이라면 개수를 숨기고 로딩·오류 상태를 제공한다.
- 펼친 목록에서 업체 행을 선택하는 동작(Q15)과 `GET /api/v1/vendors/{id}`를 자동 호출할지는 승인 전까지 정하지 않는다.

## Q15~Q24 추가 API 변경 요구 (2026-11-04 / 기능 승인, 서버 미구현)
- **Q15 / Q16 / Q20 / Q21 / Q23:** 화면 상태·카메라·시트·빈 결과·저장 UI 정책이다. 저장 지속성은 별도 `/saved` 기능 API/DB 설계에서 다룬다. 이 결정만으로 업체 검색 신규 엔드포인트가 생기지는 않는다.
- **Q17:** 검색어 키보드 제출 시에만 `appliedBounds + query + filters`로 조회. 현재 HTTP API는 사용자 타이핑 이벤트를 알 필요 없음.
- **Q18:** 현재 `category`는 존재하지만 별도 품목 필터와 배송 가능 필터는 독립 파라미터가 없다. `fulfillment` 값(pickup/delivery/both) 및 품목 매칭 정책, 파라미터 이름/기본값/조합 규칙을 Zod·RPC·모바일 계약으로 일괄 정의해야 한다.
- **Q19:** 기본 거리순 유지, 품목 검색 시 가격순 정렬 선택 허용. **서로 다른 규격과 다중 일치 품목을 어떤 가격으로 비교할지 미확정**이다. 계약 확정 전 `sort=price`를 무조건 지원하는 것으로 표시하거나, 첫 품목/최저 품목 가격을 임의 정렬 키로 정하지 않는다.
- **Q22:** `가격 문의` / `배송 정보 없음`은 데이터가 없을 때의 화면 문구다. 현행 공개 품목 DTO의 `price: number`는 필수이므로 실제 미확인 가격을 표현하려면 선택적/nullable 가격이 필요한지 도메인·DB·API를 먼저 검토한다. 금액 0과 정보 미제공은 구분한다.
- **Q24:** 지도 전체 결과(클러스터 계산 대상)와 20건 단위 목록 결과를 같은 검색 조건에 대해 제공해야 한다. 전체 조회를 서버 분할/경량 마커/집계로 최적화해도 임의 상한으로 업체를 빠뜨린 뒤 전체라고 표기하지 않는다. **최대 범위·총량, 타일/집계 데이터 계약·클라이언트 완전성 표시**는 별도의 성능 설계에서 정의한다.
- **호환성:** 현행 `GET /api/v1/vendors`의 `latitude/longitude/radius` 요청은 기존 구현된 사실이고, 미구현 `bounds`/배송/가격순은 **예정 요건**이다. 릴리스 전 계약 테스트를 통과해야 한다.
