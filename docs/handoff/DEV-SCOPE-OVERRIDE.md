# dev 전용 작업 범위 — 2026-11-04 사용자 승인

> **적용 범위는 `dev` 브랜치뿐이다.** 이는 팀 채택 ADR이나 `main`의 수정 승인이 아니며, 본 패키지는 명세 문서이지 구현이 아니다.

## 확정된 우선 규칙
1. **기존 Supabase 프로젝트/DB 재사용은 필수.** 이미 존재하는 업체·품목·가격·승인·공공 원문 데이터와 기존 테이블·RLS·RPC·스토리지·마이그레이션을 보존하고, 실제 연결을 확인한 후 그 DB를 기준으로 새 기능을 붙인다. 새 프로젝트나 독립 DB로 이전하는 것은 기본 선택이 아니며 임의로 진행하지 않는다.
2. **기존 모바일/웹/API 앱 소스코드 재사용은 선택.** 기존 코드를 읽고 재사용·교체·새 구현 중 설계상 적합한 방식을 제안할 수 있다. 기존 앱 코드를 그대로 써야 할 의무는 없다. 단, DB 호환성, 기존 팀원 소유 코드, 관련 모듈/계약의 영향을 먼저 분석하고 변경 허가 없이 삭제·덮어쓰지 않는다.
3. **`dev`에서만 작업한다.** `dev`는 `차승호` 브랜치 기반이고 `main`의 최신 커밋 병합은 요청되지 않았다. `main`에 커밋·푸시·PR 병합·강제 push/리베이스/브랜치 삭제를 하지 않는다. 작업 전 GitHub 화면과 `git branch --show-current`로 대상이 `dev`인지 확인한다.
4. **기존 DB를 초기화·삭제·재생성·테이블 재정의하지 않는다.** 기존 SQL migration 재실행/수정 금지. 새 테이블·RPC·RLS 등 필요 시 기존 DB에 부가적으로 적용하는 새 migration을 설계하되, 실제 적용은 팀/DB 소유자 승인과 비파괴 검증 후만 한다.
5. **시연용 쓰기 데이터는 기존 DB 안에서 논리적으로 격리한다(구체 구조 제안 단계).** 운영 테이블과 별도의 시연 테이블/세션 범위 및 RLS·Storage 정책을 설계한다. 시연 초기화는 해당 시연 세션의 데이터에만 한정하며 업체·가격·등록/검토 데이터는 절대 지우지 않는다. 구조와 공유 DB 권한은 구현 전에 검증/승인받는다.
6. 사용자 로그인 화면은 없음. **내부 인증/소유권 검사와 RLS는 유지**해야 하며 익명 인증으로 운영 등록·심사 권한이 열리면 작업을 중단한다.
7. 이번 데모 구현: 지도/업체 상세, 근거 기반 실제 LLM AI, 커뮤니티, 저장. **내 정보·업체 관리 = UI만**. 업체 등록·승인 신규 백엔드는 범위 제외, 기존 기능/데이터는 보존.
8. 사용자에게 불명확하거나 충돌하는 중요한 사실·기술·외부 키·DB 권한이 발견되면 **임의 선택하지 말고 질문하고 중단**한다.

## 문서 충돌 시 판단
- 이번 사용자 승인 dev 작업 범위는 **본 파일이 우선**, 그 밖의 기존 사업 근거·과거 팀 규칙은 보존한다.
- `SPEC.md`, `ontology.yaml`, 팀 ADR은 과거 연구·구현 문맥이므로 이 문서만으로 팀 전체 합의가 바뀐 것은 아니다. 새 기능/API/DB 설명은 구현 전까지 제안(PROPOSED)이다.
- 구현 DB 계약은 실제 적용된 Supabase 스키마/RLS/RPC와 현재 배포된 서버 응답을 조사하여 확정한다. 문서상 DDL이 실제 DB에 적용됐다고 가정하지 않는다.
- 신규 앱 코드 구조는 기존 `apps/mobile`, `apps/cheonhajangsa`에 묶일 의무는 없지만, DB 공개 조회 계약과 팀 협업 원칙은 유지한다.
