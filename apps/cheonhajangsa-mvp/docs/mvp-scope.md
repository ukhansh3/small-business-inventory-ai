# MVP 범위

> 우선순위 1위 문서. 다른 문서와 충돌하면 이 문서가 이긴다. 충돌은 `consistency-report.md`에 기록한다.
> 원천: `planning/시연기획서.md`, `planning/개발기획서.md`(이하 기획서), `planning/API명세서.md`, `planning/DB아키텍처.md`.

## 1. 목표
5일 안(2026-11-04 ~ 11-09) 배포 링크 하나로 다음 흐름이 끝까지 동작한다.

> 사장님이 '상추'를 입력 → AI가 양·급함·받는 방식을 선택지로 되묻는다 → 근처 상추 판매처가 거리·영업 상태·입고 시간·가격(보조)과 함께 나온다 → 한 곳을 골라 '전화하기'.

강의실 Windows PC 브라우저(Chrome·Edge)에서 설치 없이 링크로 시연한다(11/11 중간평가②).

## 2. 기능 우선순위

| P0-2 | 검색 함수(R-01~R-11, R-15): 최소 판매량, 영업·입고 판정, 받는 방식, 거리, 정렬, 가격 문구 | 기획서 4절, AC-1·2·4·7·8·9·12 |
| P0-3 | `POST /api/v1/search` (API-02) | API 명세 |

| P0-5 | 저장된 응답 모드(`AI_MODE=stored`)와 AI 실패 시 칩 편집으로 이어 가기 | WF-12, AC-15 |
| P0-6 | 화면: 대화(S-01), 조건 칩(S-02), 결과 목록(S-03), 범위 밖 안내(S-05), 예시 데이터 띠 | 기획서 6절 |

## 3. 명시적 제외 (5일 범위 밖)
- 기획서 [다음] 전부: 운영자 로그인·관리(API-08~10, 12), 판매처 직접 갱신(API-11), 현장 확인·사용자 테스트 기록, 판매처 데이터의 DB 이전(DB아키텍처 0002 마이그레이션), 음성 입력(API-13)
- 로그인, 결제·주문, 별점, 커뮤니티·팔로우, 상추 외 품목 검색(지도는 v2에서 범위 안으로 옮김, 5절)
- 휴대폰 네이티브 빌드(APK·스토어). 코드는 Expo라 가능하지만 이번 범위에서 검증하지 않는다

## 5. v2 범위 (2026-11-04 결정, 11/11 발표까지) — 상세 `feature-v2.md`
v1 흐름(상추 찾기)은 그대로 두고 아래를 더한다. "우리 걸 왜 써야 하나"에 답하는 핵심은 V2-1이다.

| ID | 기능 | 우선 |
|---|---|---|
| V2-1 | 단가 진단: 사진(영수증·모바일 영수증·플랫폼 결제내역·상품 화면) → 줄별 kg당 가격 → 동네 시세 대비 판정 → 더 싼 곳(API-15, R-16~R-21) | 필수 |
| V2-2 | 가격 한 줄 진단: "상추 2키로 만원" → 같은 진단(API-01 `check_price`) | 필수 |
| V2-3 | 동네 시세 한 줄: 찾기 결과 위에 kg당 범위·중간값·건수(API-17, R-18) | 필수 |
| V2-4 | 시세에 보태기 동의(API-16). 사진 원본·원문은 저장하지 않음(R-21) | 필수 |
| V2-5 | 공공데이터 가게 수집(영통구+팔달구, 식자재 관련 업종) → `data/public_stores.json` | 필수 |
| V2-6 | 지도 홈: 카카오맵 + 아래 목록 시트, 입력창 하나(찾기·가격 한 줄·사진), 핀(판매처·예시·공공데이터·내 위치), API-18 | 필수 |
| V2-7 | 이미지 evals(합성 영수증 10장+), E2E에 진단 흐름 추가 | 권장 |

v2에서 빠지는 것: 상추 외 품목 시세, 판매처 직접 가격 등록, 리뷰, 카카오 장소 정보(번호 등), 길찾기, 네이티브 지도, 사진 원본 보관.
자를 순서(일정 지연 시): V2-7 → 지도 목록 시트(고정 지도+목록으로 단순화) → 공공데이터(예시 판매처만 지도에) → V2-3. V2-1·V2-2는 자르지 않는다.
