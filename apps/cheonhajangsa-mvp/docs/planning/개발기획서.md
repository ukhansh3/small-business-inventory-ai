## 3. 데이터 개체 (DB 설계의 원천)

저장 위치: [MVP] 판매처·품목·판매 정보·위치 프리셋은 앱 안 데이터 파일(`data/*.json`). 사장님·대화·기록·요청은 **내 Supabase 프로젝트**(팀 DB와 분리). [다음] 판매처·판매 정보도 같은 Supabase로 옮긴다.

공통 칸: 모든 개체는 `id`(문자열 또는 uuid), `created_at`, `updated_at`(시각은 ISO 8601, 한국 시간 기준 표시)을 가진다. 아래 표에서는 생략한다.

### E-01 품목 (item) [MVP]
| 칸 | 타입 | 필수 | 허용값·설명 |
|---|---|---|---|
| name | 문자열 | 예 | 대표 이름. 예: 상추 |
| aliases | 문자열 목록 | 예 | 같은 뜻의 말. 예: 청상추, 적상추, 꽃상추 |
| category | 문자열 | 예 | 채소 |
| active | 참/거짓 | 예 | 참이면 검색 가능. 상추만 참 [MVP]. 거짓인 품목은 '요청 남기기' 대상 |
| default_unit | 문자열 | 예 | kg |

[MVP]에서 거짓 품목도 몇 개 넣어 둔다(대파·양파·깻잎·고추). AI가 '대파'를 알아듣고 "아직 없음"으로 안내하는 데 쓴다.

### E-02 판매처 (vendor) [MVP]
| 칸 | 타입 | 필수 | 허용값·설명 |
|---|---|---|---|
| name | 문자열 | 예 | 가게 이름 |
| kind | 문자열 | 예 | `채소가게` / `식자재마트` / `시장점포` |
| address | 문자열 | 예 | 도로명 주소 |
| dong | 문자열 | 예 | 동 이름. 배달 지역 판정에 쓴다 |
| lat, lng | 실수 | 예 | 좌표 |
| phone | 문자열 | 예 | 가게 공개 번호. 전화하기에 쓴다 |
| opening_hours | 요일별 목록 | 예 | 요일마다 `{open: "07:00", close: "20:00"}` 또는 `closed`. E-02a 참고 |
| delivery_available | 참/거짓 | 예 | 배달을 하는가 |
| delivery_dongs | 문자열 목록 | 아니오 | 배달 가능한 동. `delivery_available`이 참일 때만 |
| delivery_note | 문자열 | 아니오 | 예: 2만 원 이상 배달 |
| data_status | 문자열 | 예 | `예시` / `현장확인` / `판매처직접` |
| checked_on | 날짜 | 아니오 | 판매처 정보 전체를 마지막으로 확인한 날 |

#### E-02a 영업시간 표현
- 요일 7개(`mon`~`sun`)마다 하나. 값은 `{open, close}`(24시간 표기, 한국 시간) 또는 `closed`.
- 자정을 넘기는 영업(예: 20:00~02:00)은 `close`가 `open`보다 작으면 다음 날로 본다.
- 임시 휴무는 [다음] E-11 변경 이력으로 처리한다.

### E-03 판매 정보 (offer) [MVP]
한 판매처가 한 품목을 어떻게 파는지. 판매처와 품목의 짝마다 하나.

| 칸 | 타입 | 필수 | 허용값·설명 |
|---|---|---|---|
| vendor_id | 참조 | 예 | E-02 |
| item_id | 참조 | 예 | E-01 |
| price | 정수(원) | 아니오 | 비면 가격 정보 없음 |
| price_unit_label | 문자열 | 아니오 | 가게가 적은 단위 그대로. 예: `1kg`, `1박스(4kg)`, `1소쿠리` |
| unit_kg | 실수 | 아니오 | 그 단위가 몇 kg인가. 모르면 비움(환산 안 함) |
| price_source | 문자열 | 아니오 | `가게안내` / `현장확인` / `판매처직접` / `예시` |
| price_checked_on | 날짜 | 아니오 | 가격을 확인한 날 |
| min_sale_kg | 실수 | 아니오 | 최소 판매량(kg). 비면 '최소 판매량 미확인' |
| restock_days | 요일 목록 | 아니오 | 입고하는 요일. 예: 월~토 |
| restock_time | 시각 | 아니오 | 입고 시각. 예: 07:00 |
| last_restocked_on | 날짜 | 아니오 | 마지막으로 입고된 날. 오늘 입고 판정에 쓴다(R-05) |
| available | 참/거짓 | 예 | 지금 팔고 있는가. 거짓이면 결과에서 뺀다 |

유일 조건: (vendor_id, item_id) 한 쌍에 하나.

### E-04 위치 프리셋 (location) [MVP]
| 칸 | 타입 | 필수 | 허용값·설명 |
|---|---|---|---|
| name | 문자열 | 예 | 예: 아주대 정문, 아주대 삼거리, 우만동 주민센터 |
| dong | 문자열 | 예 | 동 이름 |
| lat, lng | 실수 | 예 | 좌표 |
| is_default | 참/거짓 | 예 | 아주대 정문만 참 |

### E-05 기기 (device) [MVP, Supabase]
| 칸 | 타입 | 필수 | 허용값·설명 |
|---|---|---|---|
| id | uuid | 예 | 첫 실행 때 브라우저가 만들어 저장. 서버는 처음 받으면 등록 |
| location_id | 참조 | 예 | 내 위치(E-04). 기본은 아주대 정문 |
| business_type | 문자열 | 아니오 | 사장님이 고른 업종. 선택 사항 |
| first_seen_at, last_seen_at | 시각 | 예 | — |
| is_test | 참/거짓 | 예 | 팀원·리허설 기기면 참. 목표 측정에서 뺀다 |

개인정보는 받지 않는다(이름·전화번호·정확한 주소 없음).

### E-06 대화 세션 (session) [MVP, Supabase]
| 칸 | 타입 | 필수 | 허용값·설명 |
|---|---|---|---|
| device_id | 참조 | 예 | E-05 |
| started_at, ended_at | 시각 | 예 / 아니오 | — |
| ai_mode | 문자열 | 예 | `live`(실제 호출) / `stored`(저장된 응답) |
| model | 문자열 | 예 | 예: claude-haiku-5-5 |
| prompt_version | 문자열 | 예 | 시스템 프롬프트 버전. evals 비교에 쓴다 |
| data_version | 문자열 | 예 | 데이터 파일 버전(커밋·해시). evals 비교에 쓴다 |
| ai_calls | 정수 | 예 | 이 세션의 AI 호출 수. 6회 상한(7절) |
| outcome | 문자열 | 아니오 | `results`(결과 보여줌) / `out_of_scope_item` / `off_topic` / `ai_failed` / `abandoned` |

### E-07 대화 턴 (turn) [MVP, Supabase]
| 칸 | 타입 | 필수 | 허용값·설명 |
|---|---|---|---|
| session_id | 참조 | 예 | E-06 |
| seq | 정수 | 예 | 0부터 |
| role | 문자열 | 예 | `user` / `assistant` |
| kind | 문자열 | 예 | `text`(사장님 입력. 입력 수단 `typed`/`voice`는 [다음]) / `choice`(선택지 고름) / `ask`(AI 되묻기) / `notice`(안내) / `results`(결과 제시) |
| text | 문자열 | 아니오 | 입력 문장 또는 AI 문장 |
| ask_slot | 문자열 | 아니오 | 되묻는 조건: `qty` / `urgency` / `fulfillment` |
| options | 목록 | 아니오 | 되묻기 선택지 |
| chosen | 문자열 | 아니오 | 사장님이 고른 선택지 |
| latency_ms | 정수 | 아니오 | AI 응답 시간 |

### E-08 조건 (condition) [MVP, Supabase]
세션마다 마지막 확정 조건. 조건이 고쳐지면 새 버전으로 쌓는다(version).

| 칸 | 타입 | 필수 | 허용값·설명 |
|---|---|---|---|
| session_id | 참조 | 예 | E-06 |
| version | 정수 | 예 | 1부터. 칩 수정마다 +1 |
| item_id | 참조 | 예 | E-01 |
| qty_kg | 실수 | 아니오 | 원하는 양 |
| urgency | 문자열 | 예 | `now` / `today` / `tomorrow` |
| fulfillment | 문자열 | 예 | `pickup` / `delivery` |
| location_id | 참조 | 예 | E-04 |
| field_source | 객체 | 예 | 칸마다 출처: `said`(문장에 있었음) / `asked`(되물어 고름) / `default`(기본값) / `edited`(칩으로 고침) |

`field_source`는 evals와 '지어낸 값' 검사에 쓴다. AI가 `said`라고 했는데 문장에 없으면 지어낸 것이다.

|---|---|---|---|
| session_id | 참조 | 예 | — |

| result_count | 정수 | 예 | — |

### E-10 행동 기록 (event) [MVP, Supabase]
| 칸 | 타입 | 필수 | 허용값·설명 |
|---|---|---|---|
| device_id | 참조 | 예 | — |
| session_id | 참조 | 아니오 | — |
| type | 문자열 | 예 | 아래 목록 |
| vendor_id | 참조 | 아니오 | 판매처와 관련된 행동이면 |
| payload | JSON | 아니오 | 행동별 추가 값 |

| type | 언제 | payload |
|---|---|---|
| `app_open` | 앱 열 때 | 화면 폭 |
| `location_set` | 내 위치 바꿀 때 | location_id |

| `vendor_view` | 판매처 상세 열 때 | 결과에서 몇 번째였나 |
| `call_click` | 전화하기 누를 때 | 결과에서 몇 번째였나, 거리 |
| `request_item` | 요청 남기기 누를 때 | E-12 id |
| `restart` | 새 검색 시작 | — |

### E-12 품목 요청 (item_request) [MVP, Supabase]
| 칸 | 타입 | 필수 | 허용값·설명 |
|---|---|---|---|
| device_id | 참조 | 예 | — |
| session_id | 참조 | 아니오 | — |
| requested_text | 문자열 | 예 | 사장님이 말한 그대로. 예: 대파 |

### E-13 현장 확인 (field_check) [다음]
가장 위험한 가정(판매처 정보를 모을 수 있는가)의 측정 단위. 시연기획서 7절.

| 칸 | 타입 | 필수 | 허용값·설명 |
|---|---|---|---|
| vendor_id | 참조 | 예 | 기존 판매처 또는 새로 만든 판매처 |
| visited_on | 날짜 | 예 | — |
| visitor | 문자열 | 예 | 팀원 이름 |
| consent | 참/거짓 | 예 | 동의를 받았는가. 거짓이면 아래 값을 저장하지 않는다 |
| restock_confirmed | 참/거짓 | 예 | 입고 시간을 확인했나 |
| phone_confirmed | 참/거짓 | 예 | 연락처를 확인했나 |
| price_confirmed | 참/거짓 | 예 | 가격을 확인했나(덤) |
| secured | 참/거짓 | 예 | 입고 시간과 연락처를 모두 확인하면 참 |
| memo | 문자열 | 아니오 | — |

## 4. 규칙 (코드가 강제)

AI가 판단하지 않는다. 반드시 지켜야 하는 것은 검색 함수가 코드로 처리한다(강의 6: 지켜야 하는 것은 검색에 맡기지 않는다).

| 번호 | 규칙 | 정의 | 연결 |
|---|---|---|---|
| R-01 | 판매 중인 것만 | E-03 `available`이 거짓이면 결과에서 뺀다. 요청 품목의 판매 정보가 없는 판매처도 뺀다 | — |
| R-02 | 지어내지 않기 | 결과에 나오는 모든 값(가게·가격·입고·연락처)은 데이터에 있는 값이다. 없으면 '정보 없음'으로 쓴다 | AC-6 |
| R-03 | 최소 판매량 | 원하는 양(`qty_kg`)이 판매처의 `min_sale_kg`보다 작으면 뺀다. 양을 정하지 않았거나 `min_sale_kg`가 비면 빼지 않고 '최소 판매량 미확인' 표시 | AC-1 |
| R-04 | 영업 중 판정 | 지금(한국 시간)이 오늘 요일의 `open`~`close` 사이면 영업 중. `closed`면 영업 안 함. 자정 넘김은 E-02a | AC-7 |
| R-05 | 오늘 입고 판정 | `last_restocked_on`이 오늘이면 '오늘 입고됨'. 아니고 오늘이 `restock_days`에 들고 `restock_time`이 아직 안 지났으면 '오늘 HH:MM 입고 예정'. 둘 다 아니면 입고 표시 없음 | AC-8 |
| R-06 | 급함에 따른 범위 | `now`: 영업 중인 곳을 위 묶음, 닫힌 곳은 빼지 않고 '지금은 닫힘 · 다음 영업 HH:MM' 표시 후 아래 묶음. `today`: 오늘 남은 시간에 여는 곳 위, 오늘 안 여는 곳 아래. `tomorrow`: 내일 여는 곳 위 | AC-7 |
| R-07 | 받는 방식 | `pickup`: 거리만 본다. `delivery`: 내 위치의 동이 `delivery_dongs`에 있으면 '배달 가능', 아니면 빼지 않고 '배달 안 됨' 표시 후 아래로 | AC-2 |
| R-08 | 거리 | 내 위치와 판매처 좌표의 직선거리(하버사인). 표시는 'm' 또는 'km'와 '도보 약 N분'(분당 67m, 시속 4km 기준) | — |
| R-09 | 정렬 | 묶음(R-06·R-07) 안에서: ① 오늘 입고됨 → 입고 예정 → 표시 없음 ② 가까운 순 ③ kg당 가격 낮은 순(가격 없음은 뒤) ④ 이름순 | AC-9 |
| R-10 | 가격 표시 | 가격·단위·출처·확인일이 모두 있으면 '1박스(4kg) 15,000원 · 가게 안내 · 11월 3일 확인'. 하나라도 없으면 '가격 정보 없음' | AC-4 |
| R-11 | kg당 환산 | `unit_kg`가 있으면 '(kg당 약 3,800원)'을 덧붙인다(15,000원 ÷ 4kg = 3,750원 → 100원 단위 반올림). 없으면 환산하지 않는다 | AC-4 |
| R-12 | 예시 표시 | `data_status`가 `예시`면 카드에 '예시' 표시. 화면 상단에 '예시 데이터로 보여 드려요' 띠를 항상 표시 [MVP] | — |
| R-13 | 범위 밖 품목 | 품목이 E-01에 있지만 `active` 거짓이거나 E-01에 없으면 검색하지 않는다. "아직 상추만 준비돼 있어요" + 요청 남기기 | AC-10 |
| R-14 | 무관한 말 | 식자재 찾기와 무관하면 도구를 부르지 않고 사용법을 안내한다 | AC-11 |
| R-15 | 결과 0건 | "조건에 맞는 곳이 없어요" + 어떤 조건을 바꾸면 나오는지 한 줄(예: '양을 1kg으로 줄이면 2곳') | AC-12 |

## 5. 워크플로우

각 워크플로우는 같은 틀로 적는다: 목적 / 행위자 / 시작 / 단계 / 분기 / 실패 / 끝 상태 / 읽는 데이터 / 쓰는 데이터 / API / AC.

### WF-01 첫 실행과 익명 id [MVP]
- 목적: 로그인 없이 기기를 구분한다.
- 행위자: 사장님, 서버
- 시작: 앱을 처음 연다(브라우저 저장소에 id 없음).
- 단계:
  1. 앱이 uuid를 만들어 브라우저 저장소에 둔다.
  2. 앱이 서버에 기기 등록을 요청한다(API-06).
  3. 서버는 E-05를 만든다. 내 위치는 기본값(아주대 정문).
  4. 첫 화면(S-01)에 짧은 안내: "사장님, 필요한 재료를 한 마디로 말씀해 주세요."
- 분기: 이미 id가 있으면 등록 생략, `last_seen_at`만 갱신.
- 실패: 서버 등록 실패해도 앱은 계속 쓴다. 다음 요청 때 다시 등록.
- 끝 상태: 기기 id 있음, 내 위치 = 아주대 정문.
- 읽기: E-04 / 쓰기: E-05, E-10(`app_open`)
- API: API-06
- AC: —

### WF-02 내 위치 바꾸기 [MVP]
- 목적: 거리를 사장님 가게 기준으로 계산한다.
- 행위자: 사장님
- 시작: 상단 '내 위치: 아주대 정문 ▾'를 누른다.
- 단계: 위치 프리셋 목록(S-06, API-14)에서 하나 고름 → 저장 → 진행 중인 결과가 있으면 다시 검색(WF-08과 같은 경로).
- 분기: 업종도 고를 수 있다(선택 사항).
- 실패: 저장 실패 시 이번 화면에서만 적용하고 알림.
- 끝 상태: E-05 `location_id` 변경.
- 읽기: E-04 / 쓰기: E-05, E-10(`location_set`)
- API: API-14, API-07
- AC: —

### WF-03 한 마디 입력과 의도 판별 [MVP]
- 목적: 사장님 말이 상추 찾기인지, 다른 품목인지, 무관한 말인지 가른다.
- 행위자: 사장님, 서버, AI
- 시작: 입력창(S-01)에 문장을 쓰고 보낸다. 예: '상추', '상추 2키로 급해요', '대파 있어요?', '오늘 날씨 어때'
- 단계:
  1. 앱이 세션이 없으면 새로 만든다(E-06).
  2. 서버가 품목 사전(E-01 이름·별칭)에서 문장의 품목 후보를 찾는다(RAG: 사전 검색 결과를 AI에 같이 넘긴다).
  3. 서버가 AI에 문장, 품목 후보, 지금까지의 조건, 내 위치를 넘긴다.
  4. AI는 셋 중 하나로 답한다(7절 응답 형식):
     - `ask`: 상추이고 빠진 조건이 있다 → WF-04
     - `call_tool`: 상추이고 조건이 다 있다 → WF-05
     - `notice`: 범위 밖 품목(WF-10) 또는 무관한 말(WF-11)
- 분기: 문장에 이미 있는 조건(예: '2키로', '급해요')은 `said`로 채우고 되묻지 않는다.
- 실패: AI 오류·시간 초과 → WF-12
- 끝 상태: 세션의 다음 행동이 정해짐.
- 읽기: E-01, E-05 / 쓰기: E-06, E-07(`text`)
- API: API-01
- AC: AC-5, AC-10, AC-11

### WF-04 되묻기 [MVP]
- 목적: 빠진 조건을 선택지로 채운다. 타자가 익숙하지 않은 사장님도 고르기만 하면 된다.
- 행위자: AI, 사장님
- 시작: WF-03에서 `ask`.
- 되묻는 순서와 선택지(빠진 것만, 이 순서로):

| 순서 | 조건(slot) | 질문 | 선택지 | 저장 값 |
|---|---|---|---|---|
| 1 | qty | 얼마나 필요하세요? | 1kg / 2kg / 5kg / 1박스(4kg) / 잘 모르겠어요 | 1 / 2 / 5 / 4 / 비움 |
| 2 | urgency | 언제까지 필요하세요? | 지금 바로 / 오늘 안 / 내일 | now / today / tomorrow |
| 3 | fulfillment | 직접 가지러 가세요, 배달이 필요하세요? | 직접 갈게요 / 배달해 주세요 | pickup / delivery |

- 단계: AI가 질문과 선택지를 보냄(E-07 `ask`) → 사장님이 버튼을 누름(E-07 `choice`) → 서버가 조건에 `asked`로 기록 → 다음 빠진 조건. 모두 차면 WF-05.
- 분기: 사장님이 버튼 대신 글로 답하면(예: '3키로') AI가 해석해 채운다. 해석이 안 되면 같은 질문을 한 번 더, 그래도 안 되면 기본값(qty 비움, urgency `today`, fulfillment `pickup`)을 `default`로 채우고 진행.
- 실패: WF-12
- 턴 상한: 한 세션에서 되묻기는 최대 3번(조건 3개). 넘으면 기본값으로 진행.
- 끝 상태: 조건 완성.
- 읽기: E-08 / 쓰기: E-07, E-08
- API: API-01
- AC: AC-5

### WF-05 검색 실행 [MVP]
- 목적: 확정된 조건으로 판매처를 찾는다.
- 행위자: AI(도구 호출), 서버(검색 함수)
- 시작: 조건이 다 찼다.
- 단계:
  1. AI가 `search_vendors`를 호출한다(7절 도구 정의).
  2. 서버가 인자를 검증한다(품목 id가 active인가, 값이 허용 범위인가).
  3. 검색 함수가 R-01~R-11을 적용해 결과 목록을 만든다.
  4. 결과를 E-09에 기록하고 화면에 보낸다(E-07 `results`).
- 분기: 인자가 잘못되면 `invalid_input`으로 기록하고 AI에 오류를 돌려 한 번 다시 부르게 한다. 두 번째도 틀리면 WF-12.
- 실패: 결과 0건 → R-15 안내(실패가 아니라 정상 결과).
- 끝 상태: 결과 목록(S-03) 표시, 조건 요약 칩 표시.
- 읽기: E-01~E-04, E-08 / 쓰기: E-09, E-07, E-06(`outcome=results`)
- API: API-01(AI 경유), 내부적으로 API-02와 같은 검색 함수
- AC: AC-1, AC-2, AC-4, AC-7~AC-9, AC-12

### WF-06 결과 보기 [MVP]
- 목적: 전화할 곳을 고를 수 있게 한다.
- 행위자: 사장님
- 화면 S-03 결과 카드 한 장(위에서부터):
  1. 가게 이름 · 종류 · '예시' 표시
  2. 거리 '350m · 도보 약 5분' · 영업 상태('영업 중 ~20:00' / '지금은 닫힘 · 내일 07:00')
  3. 입고 '오늘 07:00 입고됨' / '오늘 15:00 입고 예정' / 표시 없음
  4. 받는 방식에 따라 '배달 가능' / '배달 안 됨'
  5. 가격(보조, 작게) R-10·R-11
  6. 최소 판매량 '최소 2kg부터' 또는 '최소 판매량 미확인'
  7. 버튼 [전화하기] [자세히]
- 묶음 제목: '지금 갈 수 있는 곳 N' / '지금은 닫힌 곳 N'(R-06)
- 거리 표시는 R-08, '예시' 표시는 R-12를 따른다.
- 상세(S-04): 카드 정보 + 주소, 요일별 영업시간, 배달 지역, 확인일, 데이터 출처.
- 쓰기: E-10(`vendor_view`)
- API: API-03(상세)
- AC: AC-4, AC-6

### WF-07 전화하기 [MVP]
- 목적: 성공의 정의(전화할 곳을 고른다)를 행동으로 남긴다.
- 단계: [전화하기] → 기록(E-10 `call_click`) → `tel:` 링크 열기. 휴대폰이면 전화 앱, PC면 번호를 크게 보여 주고 복사 버튼.
- 분기: 예시 데이터면 실제 전화가 걸리지 않게 '예시 번호입니다' 안내를 먼저 띄운다 [MVP].
- 쓰기: E-10
- API: API-04
- AC: AC-13

### WF-08 조건 고쳐 다시 검색 [MVP]
- 목적: AI가 틀려도 검색이 막히지 않게. AI를 다시 부르지 않는다.
- 단계: 조건 칩(예: '2kg')을 누름 → 선택지(WF-04 표와 같음) → 고르면 조건 새 버전(`edited`) → 검색 함수 직접 호출(API-02, `called_by=user_edit`) → 결과 갱신.
- 쓰기: E-08(새 버전), E-09, E-10(`condition_edit`)
- API: API-02
- AC: AC-14

### WF-09 새 검색 [MVP]
- 단계: [새로 찾기] → 세션 종료(`ended_at`) → 새 세션으로 WF-03.
- 쓰기: E-06, E-10(`restart`)

### WF-10 범위 밖 품목과 요청 남기기 [MVP]
- 목적: 지어내지 않고, 확장 요청을 측정한다.
- 시작: WF-03에서 품목이 상추가 아님(예: '대파 있어요?').
- 단계: AI가 "아직 상추만 준비돼 있어요. 대파가 필요하시면 알려 주세요" + [요청 남기기] [상추 찾기] → [요청 남기기]면 E-12 기록 + "알려 주셔서 고마워요. 준비되면 먼저 보여 드릴게요".
- 분기: 사전에 없는 말(예: '고수')도 같은 흐름. `matched_item_id` 비움.
- 끝 상태: 세션 `outcome=out_of_scope_item`.
- 쓰기: E-12, E-10(`request_item`), E-07
- API: API-01, API-05
- AC: AC-10

### WF-11 무관한 말 [MVP]
- 단계: AI가 도구를 부르지 않고 "필요한 재료를 말씀해 주세요. 예: 상추 2kg" 안내.
- 끝 상태: 세션 `outcome=off_topic`.
- AC: AC-11

### WF-12 AI 실패와 저장된 응답 모드 [MVP]
- 목적: AI가 멈춰도 시연과 사용이 이어진다.
- 실패 판정: 응답 8초 초과, API 오류, 응답 형식 깨짐, 도구 인자 2회 연속 오류.
- 대응: "잠깐 문제가 있어요. 조건을 직접 골라 주세요" + 조건 칩을 바로 펼친다(WF-08 경로). 세션 `outcome=ai_failed`.
- 저장된 응답 모드: 서버 설정 `AI_MODE=stored`면 미리 저장한 응답(시연 입력 3종)을 돌려준다. 화면 상단에 '저장된 응답' 작게 표시. 시연 중 쓰면 말로 밝힌다(중간평가② 규칙).
- 쓰기: E-06(`ai_mode`, `outcome`), E-07
- AC: AC-15

### WF-13 기록(관측) [MVP]
- 목적: evals·목표 측정·오류 분석의 원료(강의 6 관측, 강의 7 결과 기록).
- 무엇을: 모든 턴(E-07), 조건 버전(E-08), 도구 호출 입력·출력·시간(E-09), 행동(E-10), 요청(E-12).
- 원칙: 사장님 개인정보는 없다. 문장 원문은 남긴다(evals 케이스로 옮길 수 있게). 팀원·리허설 기기는 `is_test`로 구분.
- API: API-01~API-05가 각자 기록. 별도 조회 API는 [다음] API-12

### WF-14 판매처 데이터 넣기 [MVP: 파일 편집]
- 목적: 시연 데이터를 준비한다.
- 단계: 운영자가 `data/vendors.json`, `data/offers.json`, `data/items.json`, `data/locations.json`을 고친다 → 형식 검사 스크립트 실행(필수 칸·허용값·좌표 범위) → 배포.
- 규칙: 가상 판매처는 `data_status: 예시`, 가격 출처 `예시`. 실제 가게 이름·번호를 허락 없이 쓰지 않는다.
- AC: AC-16(형식 검사)

### WF-15 현장 확인 기록 [다음]
- 목적: 가장 위험한 가정을 측정하고, 확인된 값을 판매처 데이터에 반영한다.
- 행위자: 운영자(팀원)
- 단계: 운영자 화면(S-10) 로그인 → 판매처 고르기(없으면 새로 만들기) → 동의 여부 체크 → 입고 시간·연락처·가격 입력 → 저장. 동의가 없으면 방문 사실만 남기고 값은 저장하지 않는다.
- 결과: E-13 기록, `secured` 자동 계산. 확인된 값은 E-02·E-03에 반영(`data_status=현장확인`, 출처 `현장확인`, 확인일), E-11 이력.
- API: API-08, API-09

### WF-16 갱신 링크 발급 [다음]
- 행위자: 운영자
- 단계: 판매처 상세(S-11)에서 [갱신 링크 만들기] → 서버가 비밀값 생성, 해시만 저장(E-14) → 링크를 한 번만 보여 줌 → 운영자가 판매처 사장님께 문자로 전달.
- 분기: 링크를 잃어버리면 폐기(revoke) 후 새로 발급.
- API: API-10

### WF-17 판매처가 직접 갱신 [다음]
- 목적: 멘토가 말한 선순환. 판매처가 입고·가격을 고쳐 정보가 최신으로 유지된다.
- 행위자: 판매처 사장님
- 단계: 링크 열기(로그인 없음) → 큰 글씨 화면(S-12): '오늘 입고됐어요' 버튼, 입고 시간, 가격과 단위, '오늘 쉬어요' → 저장.
- 결과: E-03 갱신(출처 `판매처직접`, 확인일 오늘), '오늘 입고됐어요'는 `last_restocked_on=오늘`, E-11 이력(`actor=vendor_link`).
- 실패: 링크 만료·폐기면 "운영자에게 새 링크를 요청해 주세요".
- API: API-11

### WF-18 품목 추가 [다음]
- 단계: 확장 요청(E-12)이 많은 품목을 운영자가 E-01 `active=참`으로 바꾸고 판매 정보를 넣는다.
- 영향: AI 시스템 프롬프트의 품목 설명과 evals 케이스를 함께 갱신한다(prompt_version 올림).

### WF-20 음성 입력 [다음]
- 목적: 주방 잡음 속에서도 말로 입력한다(타자가 익숙하지 않은 사장님).
- 단계: 입력창의 [말하기] 누름 → 마이크 권한 → 녹음(최대 10초) → 서버가 STT로 글자 변환 → 변환된 문장을 입력창에 보여 주고 사장님이 확인 → WF-03과 같은 경로.
- STT 후보: 리턴제로 RTZR(한국어·잡음), 네이버 CLOVA Speech(한국어·구어), OpenAI 음성 인식(범용), Google Speech-to-Text(Chirp). 브라우저 내장 음성 인식은 품질 통제가 안 돼 제외.
- 고르는 방법: 우리 인터뷰 녹음(식당 잡음 속 한국어)과 사람이 고친 전사본으로 후보 2~3개를 비교. 지표는 오인식률, 품목명·숫자 정확도.
- 위험: 강의실 PC 마이크·권한. 인식 결과를 바로 검색하지 않고 사장님이 확인한 뒤 보낸다.
- 쓰기: E-07(`kind=text`, 입력 수단 `voice` 표시) / API: API-13

### WF-19 사용자 테스트 기록 [다음]
- 목적: 최종 목표(확장 요청 비율, 정성 목표)를 잰다.
- 행위자: 운영자(팀원), 개업 초기 사장님
- 단계: 동의를 받는다 → 사장님 휴대폰이나 팀원 기기로 앱을 직접 써 보게 한다(설명은 최소) → 끝나면 운영자가 E-15를 입력: 고른 판매처, 고른 이유, '다른 채소도 있나요?' 여부 → 그 기기의 E-10·E-12 기록과 맞춰 본다.
- 판정: 5명 중 3명 이상이 다른 채소를 요청하면 정량 목표 달성. 전화할 곳을 고르고 이유로 거리나 입고 시간을 말하면 정성 목표 달성.
- 쓰기: E-15 / API: API-09(운영자), API-12(내보내기)

## 7. AI 설계

### 역할 나눔
- AI: 품목 알아듣기, 문장에서 조건 뽑기, 빠진 조건 되묻기, 도구 호출 판단, 범위 밖·무관한 말 판단.
- 코드: 검색·거르기·정렬·표시 문구(R-01~R-15). AI는 결과를 꾸며 말하지 않는다. 결과 화면은 코드가 만든다.

### 오케스트레이션
workflow(코드가 순서를 정함). 단계가 '판별 → 되묻기 → 검색'으로 정해져 있어 에이전트 루프가 필요 없다(강의 6). 한 세션 최대 AI 호출 6회(판별 1 + 되묻기 3 + 도구 재시도 포함 2).

### AI 응답 형식 (서버가 검증)
| type | 언제 | 내용 |
|---|---|---|
| `ask` | 빠진 조건이 있음 | slot(qty·urgency·fulfillment), 질문, 선택지, 이미 뽑은 조건 |
| `call_tool` | 조건이 다 참 | `search_vendors` 인자 |
| `notice` | 범위 밖 품목·무관한 말 | 종류(`out_of_scope_item` / `off_topic`), 안내 문장, 알아들은 품목 이름 |

형식이 깨지면 WF-12.

### 도구 정의 `search_vendors`
| 인자 | 타입 | 필수 | 허용값 |
|---|---|---|---|
| item_id | 문자열 | 예 | 품목 후보 중 active인 것 |
| qty_kg | 숫자 | 아니오 | 0.5~50. 말하지 않았으면 생략 |
| urgency | 문자열 | 예 | now / today / tomorrow |
| fulfillment | 문자열 | 예 | pickup / delivery |
| location_id | 문자열 | 예 | 서버가 채움(사장님 설정) |

설명 문장(모델이 언제 쓸지 판단): "사장님이 찾는 품목과 조건이 모두 정해졌을 때, 조건에 맞는 근처 판매처를 찾는다." 부작용 없음(읽기).

### 시스템 프롬프트 원칙
1. 품목은 반드시 후보 목록 안에서 고른다. 없으면 `notice`.
2. 문장에 없는 값은 채우지 않는다. 되묻거나 비운다.
3. 판매처 이름·가격·입고 시간을 직접 말하지 않는다(결과는 코드가 보여 준다).
4. 짧고 쉬운 말. 한 번에 질문 하나.
5. 단위: '키로'·'킬로' → kg, '박스' → 1박스(4kg)로 묻기.

버전은 `prompt_version`으로 기록하고, 바꿀 때마다 evals를 다시 돌린다.

### 모델과 비용
기본 Claude Haiku 5.5(`claude-haiku-5-5`). evals에서 조건 정확도 90% 미만이면 Sonnet 5.5(`claude-sonnet-5-5`)와 비교. 서버에 하루 호출 상한(기본 500회)을 두고 넘으면 WF-12 대응.

## 9. 수용 기준 (골든 케이스·evals의 원천)

AC-1·2·4는 중간발표 SPEC ①②④를 이 제품에 맞게 옮긴 것이다(③ 이웃 표시는 커뮤니티 제외로 뺐다).

| AC | 조건 | 기대 | 규칙 | 검사 |
|---|---|---|---|---|
| AC-1 | 원하는 양 1kg, 판매처 A 최소 2kg | A가 결과에 없다. 2kg이면 있다 | R-03 | 골든 |
| AC-2 | 받는 방식 배달, 내 위치 원천동, 판매처 B 배달 동네 [우만동] | B가 빠지지 않고 '배달 안 됨'으로 아래 묶음 | R-07 | 골든 |
| AC-4 | 판매처 C 가격·단위(1박스 4kg)·출처·확인일 다 있음 / D는 확인일 없음 | C '1박스(4kg) 15,000원 · 가게 안내 · 11월 3일 확인 (kg당 약 3,800원)' / D '가격 정보 없음' | R-10, R-11 | 골든 |
| AC-5 | '상추' 한 마디 | qty → urgency → fulfillment 순서로 되묻는다. '상추 2키로 급해요'면 qty·urgency는 묻지 않는다 | WF-04 | evals |
| AC-6 | 데이터에 없는 값 | 결과·상세에 없는 값을 만들지 않는다('정보 없음') | R-02 | 골든 + evals |
| AC-7 | 지금 21:00, 판매처 E 07:00~20:00 | 급함 now면 E는 '지금은 닫힘 · 내일 07:00'로 아래 묶음 | R-04, R-06 | 골든 |
| AC-8 | 오늘 월요일 10:00, F `last_restocked_on`=오늘 / G 입고 월 15:00 | F '오늘 07:00 입고됨' / G '오늘 15:00 입고 예정' | R-05 | 골든 |
| AC-9 | 같은 묶음에 입고·거리·가격이 다른 4곳 | R-09 순서 | R-09 | 골든 |
| AC-10 | '대파 있어요?' | 도구 호출 0회, "아직 상추만" + 요청 남기기, 누르면 E-12 1건 | R-13 | 골든 + evals |
| AC-11 | '오늘 날씨 어때' | 도구 호출 0회, 사용법 안내 | R-14 | evals |
| AC-12 | 어떤 판매처도 조건을 못 맞춤 | '조건에 맞는 곳이 없어요' + 바꿀 조건 한 줄 | R-15 | 골든 |
| AC-13 | 전화하기 | E-10 `call_click` 1건, 예시 데이터면 '예시 번호' 안내 먼저 | WF-07 | 골든 |
| AC-14 | 칩에서 양을 1kg → 2kg | AI 호출 0회, 결과가 AC-1과 같게 바뀐다 | WF-08 | 골든 |
| AC-15 | AI 8초 초과 | 칩 편집이 열리고 검색이 이어진다 | WF-12 | 골든(AI 응답을 지연시키는 가짜로) |
| AC-16 | 데이터 파일에 필수 칸 누락·허용값 밖 | 형식 검사가 실패한다 | WF-14 | 골든 |

골든 케이스: 코드가 결정적으로 판정(검색 함수·화면 문구). evals: AI 응답 품질을 여러 케이스로 측정(조건 정확도 90%, 지어낸 값 0건, 범위 밖 거절 100%). AI가 들어가는 골든 케이스는 AI 응답을 고정값으로 바꿔 실행한다.

## 10. 비기능 요구

| 항목 | 기준 |
|---|---|
| 실행 환경 | 강의실 Windows PC의 Chrome·Edge 최신판. 설치 없이 링크로 |
| 화면 | 최대 폭 430px 가운데. 글씨 최소 16px, 버튼 높이 최소 48px |
| 응답 시간 | AI 턴 8초 안(넘으면 WF-12). 칩 검색 1초 안 |
| 시간 기준 | 한국 시간(Asia/Seoul). 서버 시간대와 상관없이 |
| 비밀값 | Claude API 키·Supabase 서비스 키는 서버 환경 변수에만. 앱 코드·저장소에 넣지 않는다 |
| 개인정보 | 사장님 개인정보를 받지 않는다. 판매처 번호는 공개 번호만. 현장 확인은 동의를 받은 값만 |
| 예시 표시 | 예시 데이터가 하나라도 있으면 상단 띠 표시 |
| 기록 보존 | 발표·평가 기간 동안 지우지 않는다. 테스트 기기는 `is_test`로 구분 |
