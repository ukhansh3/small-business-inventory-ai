# 코딩 규칙

## 1. 네이밍
- 파일: 소문자-하이픈(`item-requests.ts`), React 컴포넌트 파일은 파스칼(`VendorCard.tsx`).
- 변수·함수: camelCase. 타입: PascalCase. 상수: UPPER_SNAKE.
- API JSON 칸과 DB 칸: snake_case(API 명세·DB아키텍처 그대로). TypeScript 타입도 그 칸 이름을 그대로 쓴다(변환 계층을 두지 않는다).
- 규칙 함수에는 규칙 번호 주석 한 줄(`// R-05`).

## 2. 파일·모듈 분리
- 규칙 판정은 `core/`에만. `core/`는 React·Node·네트워크를 import하지 않는다.
- 서버 핸들러는 입력 검증 → core 호출 → 기록 → 응답. 한 파일 200줄을 넘기면 나눈다.
- 컴포넌트는 표시만. 상태와 API 호출은 `useAssist`.
- 추상화는 두 번째로 필요해질 때 만든다. 미리 일반화하지 않는다.

## 3. 타입
- `strict: true`. `any` 금지(외부 응답은 `unknown` → 검증 함수로 좁힌다).
- API 요청·AI 응답·데이터 파일은 런타임 검증(zod) 후 사용.
- 허용값은 문자열 리터럴 유니온(API 명세 허용값 그대로).

## 4. API·오류
- 경로·칸·오류 코드는 `planning/API명세서.md`와 같게. 바꾸면 명세도 같은 커밋에서 고친다.
- 오류 응답은 `{error:{code,message,detail?}}` 한 모양. `message`는 사장님용 한국어.
- 기록 실패·Supabase 미설정은 응답을 막지 않는다(로그만).
- AI 오류는 모두 503 `AI_UNAVAILABLE` + `detail.condition`.

## 5. DB·트랜잭션
- 서버만 접근(서비스 키). 앱에서 Supabase 클라이언트를 만들지 않는다.
- 스키마를 바꾸면 `supabase/migrations/`와 `planning/DB아키텍처.md`를 같이 고친다.
- 한 요청에서 여러 표에 쓰는 기록은 DB 함수 하나로 묶거나, 순서대로 쓰고 실패해도 응답에 영향 없게 한다(MVP 기록은 분석용이라 부분 실패 허용, progress.md에 기록).

## 6. 보안
- 비밀값은 환경 변수만. `.env.local`은 git 제외. `.env.example`에는 이름·설명만.
- `EXPO_PUBLIC_` 접두에는 비밀값을 넣지 않는다.
- 디버그 헤더는 `ALLOW_DEBUG_HEADERS=true`일 때만.
- 예시 데이터 전화번호는 `000-0000-0000` 형태, 예시 판매처는 `tel:`을 열지 않는다.
- AI 출력은 도구 인자로만 쓰고, 서버가 허용값을 다시 검증한다. AI 문장으로 판매처 정보를 보여 주지 않는다.

## 7. 테스트
- AC마다 테스트 하나 이상, 이름에 AC 번호(`AC-7 영업 종료 후 …`).
- 시각은 인자로 주입(`now`). 실제 시계에 기대는 테스트 금지.
- AI는 테스트에서 가짜(저장된 응답·지연·오류)로 바꾼다. 실시간 AI는 수동 확인과 evals에서.
- 기대값을 구현에 맞춰 바꾸지 않는다. 바꿀 때는 AC 근거를 커밋 메시지에 쓴다.

## 8. 금지
- 문서에 없는 기능 추가, [다음] 기능 선구현.
- skip·only가 남은 채 커밋.
- 실제 가게 이름·번호를 허락 없이 데이터에 넣기. 예외(v2, 2026-11-04 사용자 결정): 공공데이터의 공개 정보(이름·주소·업종·좌표)는 출처·기준일과 함께 표시할 수 있다. 실제 가게에 가격·입고·번호를 붙이는 것은 현장 확인·동의 후만(R-22).
- 영수증·결제내역 사진 원본이나 AI가 읽은 원문 글자를 저장·기록하기(R-21).
- 테스트·빌드 실패를 통과로 보고하기.
- 원격 저장소 push(사용자 지시 전).
